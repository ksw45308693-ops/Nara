# 고객사별 파일 리포트 설계

## 목표

`namo`는 고객사가 설정한 예약 시각마다 신규 매칭 공고를 하나의 HTML 리포트로 저장한다. 서버 관리자는 `REPORT_DIR`로 기본 저장 경로를 지정한다. 1차 버전은 외부 메일을 보내지 않는다.

## 확정 결정

- 리포트는 고객사와 예약 구간마다 하나만 생성한다.
- 리포트는 CSS를 포함한 단일 HTML 파일이다.
- 서버 관리자가 `REPORT_DIR`를 설정한다.
- 고객사는 `REPORT_DIR` 아래에서 분리된 디렉터리를 사용한다.
- 예약 구간에 신규 매칭이 없으면 파일을 만들지 않는다.
- 리포트는 자동으로 삭제하지 않는다.
- 메일 구현과 테스트는 유지하지만 실행 경로에서는 비활성화한다.
- 사용자 초대 화면은 메일 대신 복사 가능한 가입 링크를 표시한다.

## 선택한 구조

전용 `ReportRunner`가 예약 리포트를 생성한다. 기존 `DigestRunner`와 `SMTPMailer`는 삭제하지 않는다. 실행 시에는 `ReportRunner`만 스케줄러에 연결한다.

`DELIVERY_MODE`는 1차 버전에서 `report`만 허용한다. UI는 메일 항목을 **준비 중**으로 표시하고 선택을 막는다. 이후 메일 기능을 열 때 `email`을 허용하고 기존 메일 실행 경로를 다시 연결한다.

메일과 파일을 하나의 범용 인터페이스로 합치지 않는다. 리포트는 고객사별로 하나를 만들지만 메일은 수신자별로 발송하기 때문이다.

## 저장 구조

기본 경로는 다음과 같다.

```text
/var/db/namo/reports/
└── <tenant-uuid>/
    └── 2026/
        └── 09/
            └── namo-20260902-070000.html
```

수동 리포트는 같은 초에 여러 번 생성될 수 있으므로 파일명 끝에 리포트 UUID를 붙인다. 예약 리포트는 예약 구간의 고정 파일명을 사용한다.

애플리케이션은 DB에 `REPORT_DIR` 기준 상대 경로만 저장한다. 고객사 이름과 사용자가 입력한 문자열은 파일 경로에 사용하지 않는다.

디렉터리 권한은 `0750`이고 파일 권한은 `0640`이다. 소유자와 그룹은 `namo:namo`이다. `rc.d`의 `prestart`는 `REPORT_DIR`을 검사하고 기본 디렉터리를 준비한다.

파일 저장은 다음 순서를 따른다.

1. 최종 파일과 같은 디렉터리에 임시 파일을 만든다.
2. HTML을 쓰고 파일을 동기화한다.
3. 파일 권한을 `0640`으로 설정한다.
4. 임시 파일을 최종 이름으로 원자적으로 변경한다.
5. 최종 파일의 SHA-256과 상대 경로를 DB에 기록한다.

실패하면 임시 파일을 제거한다. 같은 예약 구간을 다시 처리할 때 최종 파일의 SHA-256이 같으면 생성 완료로 처리한다. 파일 작업은 Go 표준 라이브러리의 제한된 루트 파일 시스템 기능을 사용해 `REPORT_DIR` 밖의 심볼릭 링크를 따르지 않는다.

## 데이터 모델

`0007_report_delivery.sql`은 `reports` 테이블을 추가한다.

| 열 | 용도 |
|---|---|
| `id` | 리포트 UUID |
| `tenant_id` | 고객사 UUID |
| `schedule_id` | 예약 리포트의 스케줄 UUID. 수동 생성은 `NULL` |
| `due_at` | 예약 시각 또는 수동 요청 시각 |
| `trigger` | `scheduled` 또는 `manual` |
| `status` | `generating`, `generated`, 또는 `failed` |
| `relative_path` | `REPORT_DIR` 기준 상대 경로 |
| `sha256` | 완성된 HTML의 SHA-256 |
| `notice_count` | 리포트의 공고 수 |
| `attempts` | 생성 시도 횟수 |
| `last_error` | 마지막 실패 원인 |
| `generated_at` | 생성 완료 시각 |

예약 리포트에는 `(tenant_id, schedule_id, due_at)` 고유 제약을 적용한다. 수동 리포트는 각 요청을 별도 행으로 기록한다. `tenant_id`에는 기존과 같은 행 수준 보안을 적용한다.

기존 `digest_windows`는 예약 구간과 신규 매칭 스냅샷을 계속 관리한다. 기존 `deliveries`와 `recipients`는 메일 재개를 위해 유지한다.

## 예약 처리

`ReportRunner`는 다음 순서로 예약 리포트를 처리한다.

1. 고객사의 만기 스케줄을 조회한다.
2. 예약 구간과 신규 매칭 공고를 한 번 고정한다.
3. 신규 매칭이 없으면 파일을 만들지 않고 예약 구간을 완료한다.
4. `reports` 행을 `generating` 상태로 선점한다.
5. 고객사 리포트 하나를 저장한다.
6. `reports` 행을 `generated`로 변경하고 스케줄의 마지막 성공 시각을 갱신한다.

같은 예약 구간은 한 프로세스만 선점한다. 한 번의 작업 실행은 저장을 최대 세 번 시도한다. 세 번 실패하면 `failed` 상태와 오류를 남기고 자동 재시도를 멈춘다. 관리자가 재시도를 실행하면 같은 예약 구간과 같은 파일 경로를 다시 사용한다. 프로세스가 `generating` 상태에서 종료된 경우에는 서비스 복구 후 해당 예약 구간을 자동으로 회수한다.

수동 생성은 현재 열린 매칭 공고를 사용한다. 수동 생성은 스케줄의 마지막 성공 시각을 변경하지 않는다. 생성 대상이 없으면 파일을 만들지 않고 사용자에게 이유를 표시한다.

## HTML 내용

리포트는 외부 CSS, JavaScript, 글꼴, 이미지에 의존하지 않는다. HTML에는 다음 내용을 포함한다.

- 고객사 이름
- 생성 시각과 대상 구간
- 신규 매칭 공고 수
- 업무구분별 공고 수
- 공고명, 기관, 지역, 금액, 마감 시각
- 매칭 규칙과 매칭 이유
- 나라장터 원문 링크

모든 외부 데이터는 HTML escaping을 적용한다. 링크는 유효한 HTTP 또는 HTTPS 주소만 허용한다.

## 설정과 CLI

다음 환경 변수를 추가한다.

```sh
export DELIVERY_MODE='report'
export REPORT_DIR='/var/db/namo/reports'
```

`serve`는 `DELIVERY_MODE=report`와 안전한 절대 `REPORT_DIR`을 요구한다. `/`, 상대 경로, `..` 경로, 빈 경로는 거부한다. `SMTP_*`는 1차 버전에서 선택 설정이다.

다음 명령은 고객사의 수동 리포트를 생성한다.

```sh
namo generate-report --tenant <tenant-uuid>
```

`send-test-mail`은 사용법에서 숨긴다. 직접 실행하면 메일 기능이 비활성화됐다는 오류를 반환한다.

## UI

- 대시보드의 **메일 송부** 문구를 **리포트 저장**으로 바꾼다.
- **알림** 화면을 **리포트** 화면으로 바꾼다.
- 리포트 화면은 예약 요일, 예약 시각, 최근 생성 시각, 공고 수, 파일명을 표시한다.
- 고객사 관리자는 **지금 생성**을 실행할 수 있다.
- 사용자는 고객사에 속한 리포트만 목록에서 보고 다운로드할 수 있다.
- 플랫폼 관리자만 전체 `REPORT_DIR`을 확인할 수 있다.
- 메일 선택 항목은 **준비 중** 상태로 표시하고 비활성화한다.
- 사용자 초대 성공 화면은 가입 링크를 한 번 표시한다. DB에는 기존처럼 토큰 해시만 저장한다.

다운로드 엔드포인트는 DB의 `reports` 행을 먼저 조회한다. 서버는 RLS로 고객사를 확인한 뒤 `REPORT_DIR` 아래의 등록된 상대 경로만 연다. 웹 서버는 `REPORT_DIR`을 정적 디렉터리로 공개하지 않는다.

## 오류와 보안

- 파일 이름은 고객사 UUID와 서버 시각으로 만든다.
- 사용자가 입력한 파일 경로를 받지 않는다.
- `REPORT_DIR` 밖의 경로와 심볼릭 링크를 통한 경로 이탈을 거부한다.
- DB 완료 기록은 파일의 원자적 이름 변경이 끝난 뒤 저장한다.
- 파일 저장이 끝나고 DB 갱신 전에 서비스가 종료되면 SHA-256으로 결과를 확인한다.
- 다운로드는 로그인, 역할, 고객사 RLS를 확인한다. 상태를 변경하는 수동 생성 요청은 CSRF 검사를 적용한다.
- 리포트에는 세션 값, API 키, SMTP 값, 비밀번호를 포함하지 않는다.

## 검증 기준

단위 테스트는 다음 항목을 검사한다.

- 고객사와 예약 구간별 단일 생성
- 신규 매칭이 없을 때 파일 미생성
- HTML escaping과 안전한 원문 링크
- 임시 파일 제거와 원자적 이름 변경
- SHA-256 재처리
- 절대 경로 검증과 경로 이탈 차단
- 수동 생성이 예약 성공 시각을 변경하지 않는 조건

PostgreSQL 통합 테스트는 `reports` 마이그레이션, 고유 제약, 선점, 재시도, 상태 전환, 고객사 RLS를 검사한다.

HTTP 테스트는 리포트 목록, 수동 생성 권한, CSRF, 다른 고객사 다운로드 차단, 초대 링크 표시를 검사한다.

FreeBSD 검증은 다음 결과를 확인한다.

- `namo:namo`와 `0750` 디렉터리
- `namo:namo`와 `0640` HTML 파일
- 예약 시각당 파일 하나
- 서비스 재시작 뒤 중복 파일 없음
- 실제 브라우저에서 HTML 표시

## 제외 범위

1차 버전은 PDF, CSV, 메일 발송, 리포트 자동 삭제, 외부 파일 저장소, 파일 압축, 전자서명을 구현하지 않는다.
